## GitHub Actions

Файл `.github/workflows/build.yml` должен лежать именно в корне репозитория.
Структура репозитория: `client.py`, `server.py`, `android/`, `.github/` и остальные
файлы проекта рядом, без дополнительной внешней папки LANConnect_0_9.
Код и этот workflow можно загрузить после выбора доступного репозитория.

Запуск автоматически при push в main/master/codex/** или вручную через Actions.
Публичный GitHub Release не создаётся. Используются отдельные среды:

| Этап | Что запускается | Чего это не подтверждает |
|---|---|---|
| checks, Ubuntu 24.04 | Python-тесты, общий Java-код, синтаксис Android-исходников | Android API ещё не компилируются на этом этапе |
| windows, Windows Server 2022 | PyInstaller: клиент/сервер/генератор TLS; пробный запуск готовых EXE | Нет реальных микрофона, экрана и испытания Windows 10/11 на пользовательском ПК |
| android, Ubuntu 24.04 | SDK 35, AAPT2, javac, D8, zipalign, apksigner, проверка пакета | Нет установки APK на телефон или эмулятор |

Оба сборочных этапа зависят от checks. Результаты загружаются только после
успешных проверок этапа. В артефактах — выбранные EXE/APK, инструкции и JSON
с хешами/результатами; базы, пользовательские файлы и закрытые ключи исключены.
Срок хранения артефактов CI — 7 дней, независимо от срока хранения файлов чатов.
Права workflow: contents:read. Внешние Actions закреплены полными SHA коммитов.
Подготовка инструментов на сборочных машинах требует сети. Само приложение
использует выбранный локальный сервер и не требует GitHub или облака.

## Windows

```
py -3.12 -m pip install -r requirements-windows.txt
py -3.12 build_windows.py
```

Нужны Windows x64, Python 3.12, PyInstaller, Pillow и cryptography.
`build_windows.bat` выполняет подготовку зависимостей и запуск сценария.

Ожидаемые результаты в dist после реальной успешной сборки:

- LANConnect.exe — клиент;
- LANConnect-Server.exe — сервер;
- LANConnect-TLS.exe — создание локального CA/сертификата без отдельного Python;
- build-report.json — SHA-256 файлов и сведения о проверках.

Сборка использует временную папку, чтобы не заменять прежние файлы до окончания
проверок. Windows-клиент получает служебный режим `--self-test <JSON-путь>`:
проверяются загрузка Tk/ttk, Pillow/JPEG/Tk bridge, системные библиотеки и ABI.
Микрофон, захват экрана и ввод в этом режиме не включаются.

Сервер проверяется отдельным `test_packaged_server.py --exe ... --tls-tool ...`.
Тест задаёт временную базу и loopback-адрес, отправляет сообщение, прерывает и
продолжает файл, проверяет хеш/доступ/аудиотранспорт с тестовыми байтами, затем
запускает HTTPS с сертификатом от собранного TLS-инструмента. На Windows тест
завершает только собственное дерево процессов, включая bootloader PyInstaller.
Реальные пользовательские данные этим тестом не читаются.

Здесь проба выполнена **в режиме --source --tls-source на Linux**, а не из EXE.
Проверка build_windows.py --check вернула Windows build host required и Missing
PyInstaller. Поэтому пакетный Windows-тест пока остаётся невыполненным.

## Android: подпись и пакет

Обычная проверочная сборка из установленного SDK:

```
python android/build_android.py --sdk <SDK> --out artifacts/android
```

Для разработки используется локальный dev-keystore, сохраняемый по умолчанию
в ~/.lanconnect/dev-signing.jks. CI создаёт временный dev-ключ: такие APK нужны
для проверки сборки. Меняющаяся dev-подпись не подходит для последующих обновлений
одной установленной программы. Это не финальная схема распространения.

Для постоянной подписи нужны собственный сохранённый keystore и alias:

```
python android/build_android.py --sdk <SDK> --signing release --keystore <путь.jks> --out artifacts/android
```

Alias задаётся через --key-alias или LAN_ANDROID_KEY_ALIAS; пароли — через
LAN_ANDROID_STORE_PASSWORD и LAN_ANDROID_KEY_PASSWORD (при отсутствии второго
используется пароль хранилища). Пароли передаются apksigner через окружение,
не через литералы аргументов. Release-режим не создаёт новый ключ и не
переключается на dev-подпись, если ключ недоступен. Подпись сама по себе не
обозначает готовность приложения к эксплуатации.

В GitHub для ручного release_signing нужны Secrets:
LAN_ANDROID_KEYSTORE_B64, LAN_ANDROID_KEY_ALIAS, LAN_ANDROID_STORE_PASSWORD,
при необходимости LAN_ANDROID_KEY_PASSWORD. Закрытый ключ не помещается в репозиторий.
Сначала нужно получить успешную проверочную сборку, затем настраивать финальный ключ.

Проверяются minSdk 26, targetSdk 35, package/activity, отсутствие камеры и
ABI-зависимых .so, наличие ресурсов и DEX, совместимый с Android 8 формат DEX,
размеры заголовка и хеши DEX. Подпись проверяется apksigner. Итоговый APK и отчёт
заменяются только после этих проверок. Инструменты Java запускаются напрямую
из JAR, без Windows .bat-обёрток.

`android/test_apk_contract.py` использует искусственные ZIP/DEX-заголовки для
отрицательных проверок. Это **не Android APK и не тест реальной подписи**.
Реальные AAPT2/D8/apksigner в текущей среде отсутствуют. build_android.py снова
остановился на проверке SDK. Полная проверка типов Android, упаковка, подпись
и установка пока не выполнены.
